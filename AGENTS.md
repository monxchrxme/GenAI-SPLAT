# Правила работы над SPLAT!

## Перед изменениями

1. Прочитай этот файл целиком.
2. Прочитай `docs/MASTER_SPEC.md` — полный основной источник требований.
3. Прочитай `docs/PLAN.md` и `docs/STATUS.md`.
4. Прочитай `docs/DECISIONS.md`, `docs/ARCHITECTURE.md`, `docs/DESIGN_GUIDE.md`.
5. Сверь `docs/SPEC.md`, `docs/QA.md` и относящиеся к этапу файлы/тесты.
6. Сначала проверь фактическое состояние каталога и Git: статус может ошибаться.
7. При отсутствии Git не выдумывай ветку, commit hash или историю публикаций.

## Источник истины и границы

- Приоритет: явные решения заказчика → исходная концепция → мастер-ТЗ → гипотезы.
- Рабочие документы помогают применять мастер-ТЗ и не заменяют его.
- Не редактируй `docs/MASTER_SPEC.md` самостоятельно при обнаружении противоречия.
- Сообщи человеку о противоречии, запиши его и предложи минимально обратимый вариант.
- `[A]` / Approved — утверждено; `[P]` / Proposed — гипотеза; `[O]` / Open — открыто.
- `[X]` — исключено из MVP; Rejected используй только при фактическом отклонении.
- Не утверждай за заказчика новые продуктовые решения и не закрывай Open самостоятельно.
- Исторический §8 мастера не запускает S0: актуальная навигация — MASTER_SPEC и SPEC.

## Поэтапный процесс

- Первое поручение разрешает исключительно S−1: документация и учёт референсов.
- На S−1 запрещены код игры, зависимости, package.json, тестовые заглушки и деплой.
- После S−1 остановись; ожидай ручной приёмки и отдельного поручения S0.
- S0–S7 в плане — будущие этапы, а не разрешение выполнить их сразу.
- Каждый крупный этап выполняется в новом основном чате на том же каталоге.
- Мелкие исправления одного этапа выполняются в его чате.
- Один этап — одна поставка с проверками, демонстрацией, отчётом и ручной приёмкой.
- Не добавляй механики, персонажей или инфраструктуру вне принятого объёма этапа.
- Успешные автоматические проверки не заменяют приёмку геймплея человеком.
- Для S1 действует явное решение заказчика от 06.11.2026: не выполнять весь этап за один запрос. Первый ответ нового чата — только read-only аудит, план промежуточных действий и предложение ближайшего шага; без реализации и Git-изменений.
- Затем выполнять ровно одно согласованное промежуточное действие за ход: реализация в его границах, относящиеся проверки, демонстрация и остановка для одобрения дизайна/функционала. К следующему действию переходить только после явного подтверждения пользователя; «продолжай» разрешает один ближайший согласованный шаг, не весь S1.
- Замечания исправлять в текущем действии; промежуточное одобрение не означает приёмки всего S1 и не разрешает будущие этапы. Общий гейт S1 и итоговая ручная приёмка сохраняются. Внутренние технические операции/тесты согласованного действия выполнять самостоятельно.

## Архитектура и продукт

- Runtime: TypeScript strict, PixiJS, Vite, HTML/CSS HUD; статическая сборка Vercel.
- Ядро симуляции — чистый TypeScript без DOM, PixiJS и объектов рендера.
- Поток: Input → Commands → deterministic Simulation → Snapshot → Renderer/HUD.
- Рендер читает snapshot и никогда не меняет состояние симуляции.
- Seed, fixed timestep и журнал команд обеспечивают проверяемую повторяемость.
- Баланс, размеры и технические числа держи в типизированном конфиге; гипотезы помечай [P].
- Сохраняй уникальность ID, полное членство живых агентов и однократность outcome.
- Split/merge сохраняют число живых; потери только от боя; Restart создаёт чистый state.
- Запрещены runtime GenAI, backend, API, БД, React и Python в runtime MVP.
- Детерминированный EnemyController допустим; инструменты разработки не входят в игру.
- Не переносить игровую логику в WebSim; он необязателен и не runtime-зависимость.
- B-static: один безликий статичный сгусток; при обычном движении меняются координаты.
- Без глаз, конечностей, мимики, хвостов, перекатывания, деформаций и постоянных частиц.
- Арена просторная для 2–3 направлений; HUD минималистичный, без логотипа.
- Референсы — moodboard; не готовая карта, текстуры, спрайты или обязательный масштаб.

## Проверки и завершение

- На игровых этапах сохраняй нужные unit/integration и регрессионные QA-01—QA-12.
- Запускай доступные typecheck, lint, test, build и browser smoke согласно этапу.
- Устанавливай зависимости только после разрешения S0 и при необходимости.
- Не создавай фиктивных test reports; различай выполнено, не запускалось и недоступно.
- Отчёт: изменённые файлы, точные команды/результаты, ручной чеклист, ограничения.
- После работы обновляй STATUS, DECISIONS и CHANGELOG фактическими сведениями.
- Раздельно фиксируй implemented, tests_verified, awaiting_manual_acceptance.
- Accepted и принятый commit фиксируй только после сообщения человека и проверки Git.
- Оставляй 5–10 строк handoff; останавливайся на границе разрешённого этапа.

## Git и внешние действия

- Сохраняй существующие файлы и чужие изменения; избегай ненужного перезаписывания.
- Без отдельного разрешения не удаляй данные и не выполняй разрушающие действия.
- Без отдельного разрешения не выполняй push, merge, создание/подключение remote.
- Подключение GitHub/Vercel, внешние аккаунты и production deploy требуют разрешения.
- До разрешения подготовь команды/инструкции; URL и опубликованный статус не выдумывай.
- После приёмки возможен стабильный commit; main — для принятых результатов.
- Предпочтительны отдельные ветки feature/sN-name; соблюдай фактическую настройку Git.
- Токены и секреты не сохраняй в репозитории, документах или отчётах.
