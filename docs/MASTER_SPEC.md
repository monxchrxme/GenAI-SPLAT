# SPLAT! — Мастер-ТЗ для Codex и протокол поэтапной агентной разработки

**Версия:** 3.0 · **Дата:** 05.11.2026 · **Статус:** финальный пакет инструкций для инициализации репозитория и дальнейшей разработки.  
**Первая задача агента:** **ТОЛЬКО S−1 (подготовка репозитория и документов)**. S0–S7 приведены как полный план будущих итераций и **не являются разрешением реализовывать их сразу**.  
**Формат работы:** один Git-репозиторий; новый чат Codex на каждый крупный этап; ручная приёмка и фиксация статуса между этапами.

> **ВАЖНО ДЛЯ CODEX.** Этот файл является исходным мастер-документом. Если он получен как вложение в чат, сначала скопируй его **целиком, без пересказа и пропусков** в `docs/MASTER_SPEC.md`. Если файл уже находится в корне репозитория, перенеси его в `docs/MASTER_SPEC.md`, сохранив полный текст. Не подменяй исходный документ кратким конспектом. В репозитории `docs/MASTER_SPEC.md` — основной источник продуктовых требований; вспомогательные `.md` являются навигацией, рабочими спецификациями и состоянием проекта. При противоречии сообщи о нём человеку, не правь мастер-ТЗ самостоятельно.

## 0. Порядок работы Codex — обязательно прочитать до любого кода

1. **При первом запуске выполнить только S−1.** Создать файловую структуру, правила работы агента и документы. Не устанавливать npm-зависимости, не писать игру, не делать реальный деплой до разрешения S0. Если в репозитории уже есть файлы, изучить и сохранить их; изменения предлагать минимальные.
2. **После S−1 остановиться.** Предоставить список созданных файлов, матрицу соответствия исходному ТЗ и контрольный список готовности. Не переходить к S0 без явного подтверждения.
3. **Каждый этап S0–S7 выполнять в новом основном чате Codex**, открытом на том же репозитории; мелкие исправления одного этапа делать в его же чате.
4. Перед изменениями всегда прочитать `AGENTS.md`, `docs/MASTER_SPEC.md`, `docs/PLAN.md`, `docs/STATUS.md`, `docs/DECISIONS.md`, `docs/ARCHITECTURE.md`, `docs/DESIGN_GUIDE.md` и относящийся к этапу код/тесты. Начать с анализа фактического состояния; **файлы статуса могут ошибаться**.
5. **Один этап = одна ограниченная поставка**: реализация, тесты, ручное демо, отчёт, человек принимает этап, затем фиксация версий и переход к следующему. Наличие успешно выполненных тестов не заменяет согласование геймплея.
6. **Не выполнять самостоятельно** push, merge, создание/подключение удалённого репозитория, production deploy и любые действия с внешними учётными записями без отдельного разрешения. Подготовить необходимые команды и ручные инструкции; если пользователь дал разрешение и подключён доступ — действовать в рамках разрешения.
7. **Никакого генеративного ИИ в игре.** Codex — инструмент разработки. Обычный детерминированный контроллер красных врагов допустим.

### S−1.3. Требования к каждому документу

**`AGENTS.md` (приблизительно 50–100 строк):** порядок чтения файлов; источник истины; S−1 vs S0–S7; запреты расширения scope; разделение чистого ядра и Pixi; требования к тестам и ручной приёмке; не выполнять внешние/разрушающие действия без разрешения; обновлять `STATUS/DECISIONS/CHANGELOG` после работы; не выдумывать результаты; правило эскалации противоречий. Не дублировать весь MASTER_SPEC. Не использовать `AGENTS.md` как backlog.

**`docs/SPEC.md`:** компактная навигация по требованиям: продукт, функциональные FR-01—FR-09, утверждённое/предложенное/открытое/исключённое, герои и игровые границы; ссылки на разделы `MASTER_SPEC.md`. Не менять характеристики SPLAT! и не объявлять гипотезы утверждёнными.

**`docs/PLAN.md`:** полностью сохранить **все** задачи S−1 и S0–S7, номера подпунктов, результаты, QA-ID, гейты, зависимости; формат удобный для одного этапа за чат; отдельное поле `status` для каждого этапа; блок `Do not implement yet`. Не укорачивать план до 8 заголовков без подзадач. При сомнениях ссылаться на мастер и оставлять без потерь.

**`docs/ARCHITECTURE.md`:** стек TS strict + PixiJS + Vite + Vitest + Playwright + Vercel; схема Input → Commands → deterministic Simulation → Snapshot → Renderer/HUD; доменные структуры; инварианты; локальная статическая сборка; конфиг вместо магических констант; требования к производительности; границы API между модулями. Архитектурные числа и схемы, ещё не проверенные в прототипе, маркировать `[P]`.

**`docs/DESIGN_GUIDE.md`:** зафиксировать гибрид A+B и B-static; один преимущественно статичный сгусток пигмента на юнит, **без глаз, конечностей, выражений лица, постоянных частиц, перекатывания, деформаций и хвостов**; один мягкий силуэт/тень/блик; статичное перемещение только координатами; минималистичный HUD без логотипа; просторная арена для 2–3 направлений, умеренное число декораций, читаемая карта. Визуальные референсы — **moodboard**, не игровые текстуры/карты и не обязательная точная копия. **Референсы второго варианта юнитов динамичные: заимствовать характер формы, но не эффекты брызг и движения.** Не объявлять, что изображения находятся в репозитории, если их не передали. Если они предоставлены, перечислить фактические имена, пути и назначение в `design/references/README.md`.

**`docs/STATUS.md`:** шапка `updated_at`, `current_stage`, `stage_state`, `last_accepted_commit` (пока `not_available`), `working_branch`, `last_verified_checks`, `manual_acceptance`, `known_issues`, `next_stage`, `handoff_notes`; таблица этапов. Первоначально S−1 in_progress, S0–S7 not_started. **Не писать „принято“ или „тесты пройдены“ до фактического подтверждения.** При приёмке фиксировать commit hash, если существует; отсутствие Git commit не выдумывать.

**`docs/DECISIONS.md`:** запись даты, ID, статуса Approved/Proposed/Open/Rejected, основания, последствий, связанных QA. Перенести D-01—D-10 из мастер-ТЗ без изменения статусов. Новые изменения, влияющие на продукт, не утверждать за заказчика.

**`docs/QA.md`:** QA-01—QA-12, ожидаемый результат, вид тестирования (unit/integration/e2e/manual), первый этап применения, статус `not_implemented` до появления проверок. Не создавать фиктивные test reports.

**`docs/CHANGELOG.md`:** событие инициализации документов S−1; будущие записи — только о действительно сделанной работе, а не о запланированной.

**`README.md`:** что такое SPLAT!, что сейчас завершено, как начать S0, ссылки на документацию, будущие команды `npm` помечать „после S0“; не заявлять о работоспособном приложении до реализации.

### S−1.4. Проверка целостности и гейт

- Перечислить все созданные документы и подтвердить, что `MASTER_SPEC.md` содержит **полный** исходный текст (при копировании с места пользователя проверить, что текст не усечён).

- Сопоставить утверждённые решения: B-static, просторная арена, без логотипа, Vercel, без runtime GenAI, отсутствие backend, один этап за чат.
- Проверить отсутствие противоречивых обязательств (например: „выполнить S0 сейчас“ и „остановиться после S−1“). **Приоритет: на первом запуске остановиться после S−1.**

**Критерий приёмки S−1:** структура Markdown-документов создана, синхронизирована и человек утвердил её. Затем пользователь открывает новый чат Codex для S0.

## Регламент для новых чатов Codex

- **S0:** новый чат в том же проектном каталоге: «Прочитай AGENTS.md и docs/STATUS.md; реализуй ТОЛЬКО S0 из docs/PLAN.md; сначала проверь репозиторий, затем составь короткий план; соблюдай MASTER_SPEC, архитектуру и дизайн. После проверок дай чеклист ручной приёмки и остановись».
- **S1–S7:** новый чат только после приёмки предыдущего этапа; повторить шаблон с номером этапа; не нужно снова прикладывать PDF, если все документы уже в репозитории.
- **Внутри этапа:** баги и небольшие улучшения исправлять в том же чате; на следующем этапе агент сначала проверяет код/тесты, а затем сверяет их с `STATUS.md`.
- **В конце этапа:** агент обновляет `STATUS.md` (отдельно `implemented`, `tests_verified`, `awaiting_manual_acceptance`), `CHANGELOG.md`, предложенные изменения `DECISIONS.md`; не переводит этап в `accepted` без сообщения человека. Для следующего чата оставляет 5–10 строк handoff: что сделано, какие проверки запускались, что не работает, какие решения открыты, какой следующий шаг.
- **Git:** после ручной приёмки — стабильный коммит; по возможности отдельная ветка `feature/sN-name`; `main` только для принятых результатов. Агент не должен утверждать, что изменения опубликованы, если не делал push.
- **Vercel:** техническая подготовка в S0; подключение через интерфейс с разрешения пользователя; не утверждать наличие URL до фактического деплоя. После принятия этапа можно проверять preview, production — после согласования.

## Базовая игровая спецификация v2.0 — полный текст требований (не сокращать)

**Версия:** 2.0 · **Дата:** 26.10.2026 · **Статус источника v2.0:** утверждённая спецификация концепции + рабочие инженерные гипотезы, подлежащие приёмке в указанных этапах.

**Цель документа:** самостоятельная передача требований Codex. Описывает WHAT / HOW / DONE для каждого инкремента. Не содержит стенограммы обсуждений. Источники: «основная идея.pdf», «Передача функциональных требований в Agile.pdf», SPLAT_TZ_Codex v1.0, подтверждённые решения Заказчика о дизайне, стеке и деплое.

**Легенда:** [A] утверждено Заказчиком; [P] рабочий способ реализации, проверяется при приёмке; [O] решение откладывается до контрольной точки; [X] исключено из MVP. Предложение [P] не считать неизменным требованием.

## 1. Паспорт продукта, цели и границы

**SPLAT!** — браузерная 2D-стратегия с видом сверху. Синие живые фрагменты краски — Сплаты — борются с красной фракцией на постепенно обесцвечивающемся поле. Игрок управляет ограниченной численностью как одной массой: рисует построение, растягивает его, намеренно разделяет на автономные группы, выдаёт разные приказы и объединяет группы обратно. Присутствие на поле перекрашивает территорию; противостояние создаёт выбор между охватом и концентрацией сил. [A]

**Основной цикл:** старт с ограниченной армией → рисование формы → занятие позиции и перекрашивание → обнаружение нескольких направлений → split → раздельное управление → локальные столкновения → merge → достижение заданной цели → победа/поражение/повтор. Целевая игровая сессия: около 3–5 минут как ориентир, не SLA. [A]

**Герои и роль:** Капитан Блюм — обозначение стороны игрока (синий); Клякс — красной стороны; Бесцветный — сюжетная причина потери цвета, отдельный босс не обязателен. Герои не требуют индивидуальных игровых моделей, анимаций и способностей в MVP. [A/P]

**В MVP включено:** одна законченная тактическая сессия; одна просторная вручную созданная карта; базовая управляемая армия и красный противник; выбор и перестроение; растяжение; разделение и независимые приказы; объединение; окрашивание; бой и потери; UI состояния; короткое обучение, Pause, Restart, итоговый экран. [A]

**В MVP исключено [X]:** мультиплеер, аккаунты, база данных, экономика, крафт, строительство, кампания с длинным сюжетом, коллекция героев, реальная CFD/симуляция жидкости, динамический морфинг каждого юнита, непрерывные частицы движения, генерация карт, серверная игровая симуляция и **любая генеративная ИИ-функция внутри игры**. Codex и генераторы изображений применяются только как инструменты разработки и не являются частью игрового продукта.

**Условия продуктового успеха:** игрок способен осмысленно использовать минимум два направления, split/merge влияет на исход, управление понятно без объяснений разработчика, законченная короткая партия повторяема. Если базовый цикл неинтересен, не компенсировать это добавлением контента.

## 2. Художественная спецификация — утверждённая

**Общее направление [A]:** гибрид мультяшной тактической арены и насыщенной войны краски (A+B), умеренная детализация для MVP. Не делать детский/комический «маскотный» стиль.

**Юниты B-static [A]:** за основу принят визуальный характер *второго* концептуального варианта, но каждый агент — компактный статичный спрайт сгустка пигмента без глаз/лица, рук/ног и карикатурной мимики. Чёткий цельный силуэт, простая внутренняя фактура, 1 мягкая тень и 1–2 блика. Синий и красный различаются цветом и, по возможности, формой контура; фракции не полагаются только на цвет. При обычном движении спрайт **только меняет координаты**; без перекатывания, хвостов, постоянного масштабирования, деформации и частиц. [A]

**Событийные эффекты [P]:** короткое изменение яркости на урон, компактное исчезновение при гибели, единичный сигнал split/merge. Частицы допускаются только ограниченно и при необходимости — на столкновение или важное событие; в обычном перемещении запрещены. Уровень детализации и частота эффектов регулируются из конфигурации.

**Карта [A]:** существенно просторнее исходных иллюстраций, должна допускать одновременные операции минимум на 2–3 направлениях и заметную дистанцию между раздельными группами. Одна начальная карта без перегруженных объектов и лабиринтности. [P] Контрольная тестовая планировка: открытый центр, два обходных фланга, 1–2 небольших сужения, 2–4 тактически различимые зоны интереса; точные размеры/масштаб подобрать после испытаний управления.

**Арт окружения [A/P]:** нейтральная поверхность, насыщенная синяя/красная заливка, необязательные камни, кусты, руины и т. п. как декоративные референсы. Изображения из концептов не использовать как готовую карту или предписание масштаба. Приоритет — контраст и читаемость рисунка, отделения юнитов и границ контроля.

**HUD [A]:** минималистичный, без крупного логотипа на игровом экране и без тяжёлых декоративных панелей; показывать численность, число групп, условие и прогресс победы, выбранный отряд, подсказку текущего действия, Pause/Restart. Подсказки не заслоняют управление.

**Ассеты/производство [P]:** S0–S5 — отрисовка простыми PixiJS-примитивами/статичными спрайтами. На S6 — единый небольшой набор одобренных PNG/WebP/SVG-ресурсов; один стабильный спрайт на базовый тип агента фракции, без покадровых анимаций. Codex не должен самостоятельно менять художественную концепцию.

## 3. Технологический стек и архитектурные ограничения

| Слой | Решение | Назначение |
|---|---|---|
| Язык клиента | TypeScript | Основной код игры и типы |
| Графика | PixiJS | 2D WebGL/WebGPU с поддерживаемым fallback согласно установленной версии |
| Сборка | Vite | Локальный dev и статическая production-сборка |
| UI | HTML/CSS поверх canvas | Минимальный HUD и управление |
| Симуляция | Чистый TypeScript, fixed timestep | Предсказуемые состояния и проверки |
| Unit/integration | Vitest | Инварианты и логика без DOM/Pixi |
| Browser smoke | Playwright | Старт, управление, победа, рестарт |
| Качество | TypeScript strict, ESLint, Prettier | Контроль ошибок и стиль |
| Исходники | Git + GitHub | История и итерации |
| Деплой | Vercel | Статический Vite build и preview deployments |
| Backend | Нет | Не требуется для одиночной офлайн-сессии |

**Не вводить Python в runtime игры:** для браузерного MVP это усложнит стек без функциональной пользы. Допускаются независимые локальные Python-скрипты для анализа баланса/производства ассетов вне runtime; на архитектуру игры это не влияет. **Без React, API и базы данных** до изменения масштаба продукта.

**Доставка:** `npm run build` → `dist/`, GitHub → Vercel, production для main, preview для веток/PR. Подключить тестовый деплой уже в S0. При необходимости корректировать build/output settings в панели Vercel; не добавлять SSR/серверные функции. Источники в конце документа.

**Схема потока:** Pointer/Keyboard → InputAdapter → CommandQueue → Simulation.update(fixed dt) → movement → split/merge → combat → paint → outcome → immutable/render-only snapshot → PixiRenderer + HTML HUD. EnemyController отправляет команды тем же способом, но не манипулирует рендером.

**Пример структуры runtime после S0 (S−1 создаёт только документацию):**

**Модель данных (начальная, расширяемая):** `Agent{id,factionId,groupId,x,y,vx,vy,hp,alive}`; `Group{id,factionId,agentIds,formation,target,command}`; `World{width,height,obstacles,paintCells}`; `PaintCell{control,owner}`; `GameCommand{tick,type,payload}`; `MatchState{phase,tick,result}`; `LevelConfig{spawns,geometry,paint,winCondition,balancing}`; `EventLog`.

**Обязательные инварианты:** ID всех агентов уникальны; каждый живой агент ровно в одной существующей группе своей фракции; списки групп не содержат повторов и равны множеству живых агентов; split/merge не изменяет количество живых; потери возникают только от боя; пустые группы удаляются; 1 агент не делится; outcome единственный; Restart возвращает логически идентичный начальный state; рендер не меняет состояние симуляции.

**Технические параметры [P]:** фиксированный симуляционный шаг 1/60 с; ограничение количества догоняющих шагов; seed и журнал команд для реплеев; базовый тест на 40 агентах, дополнительные стресс-тесты на нескольких десятках; ориентир 60 FPS на обычном ноутбуке, допустимость 30 FPS в нагрузочном тесте — проверить инструментально; целевые браузеры — актуальные стабильные Chrome/Chromium и Firefox desktop. Все числовые параметры в конфиге.

**Управление — рабочий прототип [P]:** ЛКМ выделяет группу, drag по свободной области после выбора рисует построение, отпускание подтверждает. Разрыв: явный режим Cut (клавиша X и видимая кнопка) плюс пересечение линии построения; исследование альтернативы натяжения — только после оценки UX S2. Merge: выбрать первую группу, режим Merge, указать вторую; сближение до настраиваемой дистанции, одно объединение, сброс конфликтующих приказов. Короткий/пустой жест не вызывает ошибку и по умолчанию игнорируется. Горячие клавиши не заменяют видимых органов управления.

**Перемещение [P]:** записывать полилинию с фильтрацией соседних точек; распределить N слотов по длине; стабильно сопоставить существующих агентов и слоты; двигать с ограничением скорости и мягким разведением соседей. Никаких телепортов, реальной физики жидкости или сложного pathfinding для первой карты.

**Окрашивание [P]:** сетка PaintCell или заранее заданные зоны; посещение/нахождение агентов добавляет влияние, которое может быть оспорено красными. Owner и насыщенность выводятся из модели. Скорость, пороги, радиусы, победная доля в LevelConfig. Первая победная цель: доля контролируемых клеток; поражение: потеря всех синих агентов. Точный баланс решается S4/S5.

**Столкновения [P]:** ближайшая вражеская цель в радиусе, фиксированный cooldown и урон, удаление при HP≤0; один агент не наносит несколько ударов за одну атаку. Красные следуют простому детерминированному плану — охрана/патрулирование и реакция на ближайшую спорную область, без ML или GenAI.

## 6. Регрессионный набор QA (все тесты сохранять)

## 9. Работа с GitHub, WebSim и Vercel
